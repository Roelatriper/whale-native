# 原生版内存优化记录

历史实验日期：2026-10-31；Apple Silicon / macOS 27.0.1 / Node.js 26.8.2。以下结果来自独立库整理前的 macOS 维护版本，不是本库内置 Node 24.22.2 运行包的重新测量。仍是 AppKit + Node 第一阶段，不是已移除 Node 的第二阶段。

## 本轮结论

首先把包名、进程名和 Finder 显示名改为 `whale-native.app` / `whale-native`。ICNS 从原有 `assets/DSniang1.png` 生成，包含完整 1x/2x 表示；bundle id、配置、账本和素材目录不变。未覆盖用户 `/Applications` 里的旧副本。

内存的主要可复现开销来自会话扫描，不是设置 WebView：旧扫描每批分配最多 4 MiB Buffer，再创建 UTF-8 字符串和 split 行数组，历史扫描时造成大量瞬时分配。未结束的长聊天行还会被逐次拼接，直到达到旧的 8 MiB 限制。

现改为一个复用的 64 KiB 工作缓冲；每批处理上限仍为 4 MiB，避免无限占用 worker，但不再一次分配整批。头部也按小块读取。逐行处理不创建整批 split 数组，只前进实际读取的字节数。对已明确识别外层 type 为 response_item 的未结束聊天正文提前跳过，后续块直接找换行，不再解码或保留整段正文。

安全约束：只匹配明确的顶层前缀，不能在任意嵌套 JSON 中搜索 type；不确定时仍使用完整解析。跳过记录仍推进子任务继承历史的序号；需要的任务、错误、token、模型、UTF-8 跨块和长期任务恢复语义不变。没有降低账本精度、关闭监测、减少观测文件上限、强制 GC 或修改系统内存压力。

## 可重复的固定输入实验

命令：`npm run native:scan-memory`，等价于 `node tests/session-memory-probe.mjs --budget-mib 100`。

它在自己的临时目录生成同一份约 64 MiB 合成 JSONL，用独立 Node 进程运行真实 SessionReader；初始长任务扫描后追加 token 和完成记录，断言仅一条完成记录、输入/输出各增 10。结束清理自建目录，不读取真实会话或凭据。

| 指标 | 原实现 | 最终实现 |
| --- | ---: | ---: |
| 扫描进程峰值 RSS | 145.3 MiB | 47.1 MiB |
| 扫描后 external | 44.7 MiB | 2.4 MiB |
| 扫描后 heapUsed | 37.3 MiB | 5.5 MiB |
| 单次底层最大读取 | 4 MiB | 64 KiB |

同输入的峰值 RSS 约下降 68%。这只是独立扫描进程，不是完整应用。100 MiB 预算先在旧实现上失败，修改后通过；常规测试锁定小缓冲和功能语义，不把依赖机器/Node 版本的 RSS 数字放进普通 CI。一次处理时间约 78→29 ms，但本轮不将单次耗时声称为稳定 CPU 提升。

新增 `tests/session-reader-memory.test.mjs` 的五个回归：

1. 最大读请求、缓冲复用、长头部和活动任务。
2. 跨轮询 UTF-8。
3. 超大正文后仍处理完成记录。
4. 未结束正文不保留大字符串且继承历史序号正确。
5. 嵌套 type 不误丢真正任务事件。

## 整组 phys_footprint 对照

命令：`npm run native:measure -- --sessions --samples 3`。

统计 Swift app + Node 后台的 macOS phys_footprint；不含另行运行的正式实例。两轮均观察 24 个真实会话、1 个活动任务，但账本和余额使用隔离临时 fixture，不联网查询真实账单。真实会话会继续增长，因此不是字节完全固定的输入；固定输入因果验证以上面的合成实验为准。

| 采样时刻 | 原实现 | 最终实现 |
| --- | ---: | ---: |
| 第 10 秒 | 111.8 MiB | 139.4 MiB |
| 第 30 秒 | 91.9 MiB | 60.1 MiB |
| 第 50 秒 | 95.1 MiB | 59.8 MiB |
| Node 自身报告的峰值 | 189.9 MiB | 120.9 MiB |

稳定段这次约下降 35–37%，但第 10 秒反而较高，说明 GC/启动扫描时机仍然影响首样本，不能宣传“始终只占 60 MiB”。不同进程的各自峰值不能直接相加为整组同时峰值。真实 TLS、订阅额度、设置打开和大动图的完整峰值尚未穷尽。

原始报告保留在维护者本机临时目录，不随源码发布；含真实会话观察的报告不应公开。仅小缓冲的中间实验第 30/50 秒为 74.6/74.9 MiB。新库的合成预算测试可重复执行，不能用旧报告冒充新发行包实测。

优化前正式实例采样约 85.5 MiB（Swift 24.6、Node 60.8），正常退出后已用新的 `whale-native.app` 重启，继续使用原配置和账本。重启后的三个实际采样为 109.2 / 64.4 / 64.8 MiB；后两个样本 Swift 约 19.3、Node 约 45.2–45.6 MiB。该组有真实连接/网络及既往交互，与隔离 fixture 不同；旧实例运行年龄也不同，不能混用作严格同条件节省比例。当前真实实例稳定段约 65 MiB，不是峰值保证。RSS 与 phys_footprint 也不能混用计算一个节省率。

## 其他假设和后续工作

- 设置/浏览器脚本并非未打开就常驻载入：WebView 已按需创建并在关闭时解除所有者，旧浏览器脚本按资源请求加载。本轮不为此引入新的缓存或重写业务模块。
- 隔离原生绘制进程在第 10/30/50 秒约 19–20 MiB，未在这组静置样本中发现持续增长；不凭猜测削弱现有动画/图像质量。
- Node Worker 仍有固定开销，某些非 response_item 的大事件仍需完整解析，8 MiB 行上限并非每个会话的总内存上限。后续可按分配剖析继续做稀疏事件解析、订阅扫描复用，或进入原生业务迁移；不能简单设很低的 V8 堆上限导致 worker OOM 和丢监测。
- 需要增加长时运行、反复打开设置/动图、多活动任务的独立采样；本轮不声称完全排除泄漏。
